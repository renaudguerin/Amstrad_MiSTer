# Amstrad Plus / GX4000 ASIC ("Arnold V", AMS40489) — Implementation Reference

GX4000 support to the Amstrad MiSTer core. Compiled 2026-07-07 from:

- **[QUASAR]** Quasar Net "L'ASIC": http://quasar.cpcscene.net/doku.php?id=assem:asic (French; translated) and http://quasar.cpcscene.net/doku.php?id=dossier:plus

## 1. Lock / unlock sequence

The ASIC's extended features are gated by a lock. The lock is operated by writing a
byte sequence to the **CRTC register-select port `&BCxx`** (any `&BCxx` address).
[ARNOLD §2.11, WIKI-Unlock, QUASAR]

Sequence (17 writes total):

```
<RQ00>  <0>  FF 77 B3 51 A8 D4 62 39 9C 46 2B 15 8A  <STATE>  (<ACQ>)
```

- **Sync phase**: any **non-zero** byte (`RQ00`), then a **zero** byte. (A non-zero
  value followed by zero resets the sequence pointer.) [WIKI-Unlock, MAME]
- **13 fixed bytes**: `FF 77 B3 51 A8 D4 62 39 9C 46 2B 15 8A`
- **STATE byte**: `&CD` (205) ⇒ **UNLOCK**. Any other value ⇒ **LOCK**.
- **ACQ**: [ARNOLD] lists a final `&EE`, but [WIKI-Unlock] verified on hardware:
  *"the ASIC is already unlocked after the STATE phase, before ACQ. So ACQ is
  actually never needed."* The classic published sequence
  `FF 00 FF 77 B3 51 A8 D4 62 39 9C 46 2B 15 8A CD EE` therefore works (leading
  `FF,00` is the sync; trailing `EE` is superfluous).
- The nibbles of the sequence are generated by two 4-bit LFSR-style shift registers
  (see optimized generators in [WIKI-Unlock]); Amstrad patented the *verification*
  (GB2243701A, withdrawn 1994 — unenforceable).

Lock semantics [ARNOLD-REV §2.11, QUASAR]:

- ASIC is **locked after power-on and hard reset**.
- Locking again = same sequence with STATE ≠ `&CD`. [ARNOLD] says "same sequence
  without the terminating EE" — consistent: `...8A CD` then a byte ≠ `CD`?
  ⚠ CONFLICT (minor): [ARNOLD] implies lock = 14 bytes ending `...8A,CD`;
  [WIKI-Unlock] states lock = `...2B,15,8A` + `<any value but &CD>`. [MAME]
  implements: matching through index 13 (`&CD`) while enabled ⇒ lock, and any
  byte after `&CD` ⇒ unlock. Recommended emulator behavior: follow [WIKI-Unlock]
  (state machine advances on matching bytes; on the 14th data byte, `&CD` unlocks,
  anything else locks; sequence pointer resets on non-zero→zero sync).
- **Lock only gates RMR2** (the I/O register that pages the ASIC page in/out).
  While locked, RMR2 writes are interpreted as plain MRER (bit 5 ignored on old
  CPC). Everything already configured **keeps running** when locked: sprites stay
  displayed, DMAs keep playing, PRI keeps firing, and if the ASIC page was mapped
  when locked it **stays mapped** (and can then not be unmapped without
  re-unlocking). [ARNOLD-REV, QUASAR]

## 2. RMR2 — secondary ROM mapping register (I/O `&7Fxx`)

Gate Array port `&7Fxx`. Register select via top bits of the data byte
[ARNOLD App.1]:

| Data pattern | Register |
|---|---|
| `00xxxxxx` | Palette pointer (PENR) |
| `01xxxxxx` | Palette memory (INKR) |
| `100xxxxx` | MRER / RMR ("mode and ROM enable") |
| `101xxxxx` | **RMR2** (only when ASIC unlocked; otherwise acts as MRER) |
| `11xxxxxx` | RAM mapping (MMR / PAL function) |

RMR2 data bits (`101` + 5 bits):

| Bits | Function |
|---|---|
| D4 D3 = `00` | Low ROM at `&0000-&3FFF`, ASIC page **off** |
| D4 D3 = `01` | Low ROM at `&4000-&7FFF`, ASIC page **off** |
| D4 D3 = `10` | Low ROM at `&8000-&BFFF`, ASIC page **off** |
| D4 D3 = `11` | Low ROM at `&0000-&3FFF`, **ASIC page ON at `&4000-&7FFF`** |
| D2..D0 | Cartridge physical page (0-7) mapped as the low ROM. Default 0. |

Common values: `OUT &7F00,&B8` = ASIC page on (low ROM = cart page 0 at &0000);
`OUT &7F00,&A0` = ASIC page off. [QUASAR]

Mapping rules [ARNOLD §2.6, ARNOLD-REV, QUASAR, WIKI-ASIC]:

- The ASIC page has **priority over everything** at `&4000-&7FFF`: internal RAM,
  ROM, and expansion ROM/RAM are masked while it is on, regardless of mapping
  order. (This breaks e.g. Multiface Two.)
- ROM "write-through" (writes to ROM-mapped areas hit underlying RAM) still works
  for the relocatable low ROM, but **does not** apply to the ASIC page: writes to
  the ASIC page do not reach RAM underneath, and you cannot write-through from
  the ASIC page.
- **Hardware bug** (confirmed by gerald): if an *external* RAM expansion page is
  banked at `&4000-&7FFF` while the ASIC page is on, a write goes to **both** the
  ASIC RAM and the expansion RAM. Internal 6128+ banked RAM does not exhibit this.
  Advice in period docs: set MMR to `&7FC0` before ASIC page accesses. [ARNOLD
  (note added by CPCWiki), WIKI-ASIC]
- MRER bits keep their CPC meaning (mode, ROM enables, bit 4 = clear/reset
  interrupt counter). The two ROM-disable bits disable the low ROM *wherever* it
  is currently mapped.

### 4. Read-back / mirroring behavior (measured, [KT] + [ARNOLD-REV])

- **Sprite pixel data**: writes are masked to the low nibble; reads return
  `written & &0F`.
- **Sprite X/Y**: reads at offsets +0/+2 return the byte written. Offset +1
  (X high): if `written & 3 == 3` reads `&FF`, else reads `written & 3`
  (X is effectively 10-bit signed, −256..+767). Offset +3 (Y high): if
  `written & 1 == 1` reads `&FF`, else `written & 1` (Y is 9-bit signed,
  −256..+255).
- **Sprite register mirrors** (per 8-byte sprite slot): *writing* offsets
  +3(!), +4, +5, +6, +7 sets the **magnification** (they mirror +4)
  — ⚠ CONFLICT: [ARNOLD-REV §2.1] says "writing +3,+4,+5,+7 sets
  magnification; +4 to +7 are mirrors"; [KT] table says offsets 4,5,6,7 are all
  magnification. Treat +4..+7 as magnification mirrors, and note +3's write
  behavior needs hardware verification. *Reading* offsets +4,+5,+6,+7 mirrors
  reading +0,+1,+2,+3 respectively. [ARNOLD-REV] phrases it: reading +3 and +4
  read X position, +5 and +7 read Y position.
- **Magnification** register itself is write-only (reads give the X/Y mirrors
  above).
- **`&6800-&6807`** are write-only; reads return the same as unmapped addresses.
- **Unmapped/invalid areas & write-only regs**: a read returns **the last byte
  of the instruction performing the read** (open data bus; e.g. `LD A,(&5000)`
  returns `&50`). Same rule applies to reading write-only *I/O* ports
  (`&7Fxx`, `&BCxx`, `&BDxx`, `&DFxx`, `&EFxx`) on the Plus — and since `&7Fxx`
  decodes for read *and* write on the Plus, an `IN` on the Gate Array port
  actually performs a Gate Array **write** with that bus value ("Into the Eagles
  Nest" bug: `IN A,(C)` writes `&79` on 6128+/`&78` on 464+). [ARNOLD-REV §2.16,
  KT]
- **DCSR readable at `&6C00-&6C0F`** (whole range mirrors DCSR on read) but only
  **writable at `&6C0F`**. SAR/PPR are not readable. [ARNOLD-REV, KT, QUASAR]

## 5. Hardware sprites

[ARNOLD §2.1, ARNOLD-REV, QUASAR, KT, MAME]

- 16 sprites, 16×16 pixels, 4 bpp. Pixel value 0 = transparent; values 1-15 index
  the **sprite palette** (`&6422-&643F`). Sprite palette entry 0 does not exist.
- Pixel data: 1 byte per pixel (low nibble), row-major from top-left;
  16 bytes/row × 16 rows = 256 bytes per sprite at `&4n00`.
- **Coordinate system**: X and Y are signed 2's complement; unmagnified pixel =
  **mode 2 pixel** horizontally, 1 scan line vertically, independent of screen
  mode. X range −256..+767, Y range −256..+255. Position (0,0) = top-left of the
  *display area* (not border). With a standard 64µs/312-line screen, visible
  positions span −64..+639 (X) and −63..+199 (Y) at max magnification.
- The compare line for Y is `(CRTC_char_line << 3) | (raster_count & 7)` and the
  X compare uses the CRTC horizontal character counter: char = `(X & &FFF8)>>3`,
  pixel-in-char = `X & 7`. If CRTC R0 > 64 sprites can repeat horizontally.
  Y compare is **not** gated by Vertical Displayed (R6). [KT]
- **Magnification byte**: bits 3-2 = X mag, bits 1-0 = Y mag.
  `00`=off(not displayed), `01`=×1, `10`=×2, `11`=×4. If either X or Y mag is 0
  the sprite is off. Cleared to 0 at reset. Finest sprite = mode-2 resolution in
  15 colours (mag `0101`); largest = mode-0-width pixels × 4-line pixels
  (`1111`).
- **Priority**: border > sprite 0 > sprite 1 > … > sprite 15 > screen. Sprites
  are always in front of the main screen and behind the border. [ARNOLD §2.1,
  QUASAR] ([MAME] renders sprite 15 first and sprite 0 last, matching.)
- **Access side effects**: reading or writing a sprite's *pixel data* removes
  **that sprite only** from the display for the duration of the access (~1 byte
  width per 1µs access — the underlying lower-priority sprite/background shows
  through); the stored image is not corrupted. Writing X/Y/mag does *not* blank
  the sprite, but changing X/Y mid-display cuts the sprite and continues it at
  the new position. [ARNOLD-REV §2.1]
- No per-line sprite count limit is documented in any source (all 16 can be on
  one line).
- Sprites are unaffected by SSCR soft-scroll [ARNOLD §2.5].

## 6. Palette (32 × 12-bit)

[ARNOLD §2.2, ARNOLD-REV, QUASAR, KT]

- 32 entries × 12 bits: pens 0-15 (`&6400-&641F`), border (`&6420-&6421`),
  sprite colours 1-15 (`&6422-&643F`). 2 bytes per entry, low byte first:

```
even address (low byte):  D7-D4 = RED,   D3-D0 = BLUE
odd  address (high byte): D7-D4 = (unused, reads 0), D3-D0 = GREEN
```

  i.e. as a little-endian word: `%xxxxGGGGRRRRBBBB`. `LD HL,&0F00 : LD (&6400),HL`
  = pen 0 bright green. High byte reads back `& &0F`; low byte reads back
  exactly. [KT]
- Palette is **dual-ported**: no access-time restrictions (no snow). But a 16-bit
  CPU write is two 8-bit writes — the intermediate colour is briefly visible.
  [ARNOLD-REV note]
- **Secondary (legacy) port**: classic Gate Array PENR/INKR I/O writes still work
  for the first 17 entries (pens + border), translating the 5-bit hardware colour
  number to 12-bit RGB via a fixed ROM table (values 0-31 → 4-bit R/G/B, table in
  [KT §Palette]; e.g. hw colour 20 black = 0,0,0; 11 bright white = 15,15,15;
  mid-level = 6). Legacy writes update the ASIC palette RAM (readable there).
  Sprite colours are *not* reachable via the legacy port.
- Border colour is **undefined at power-on** (unlike CPC). [ARNOLD]
- Grey-scale/luma output weighting for mono monitors is G:R:B = 9:3:1.

## 7. PRI — programmable raster interrupt; interrupts & IVR

### PRI (`&6800`, W, POR=0)

[ARNOLD §2.4, ARNOLD-REV, QUASAR, KT]

- PRI = 0 (reset default): normal CPC Gate-Array interrupt (52-line counter)
  operates. PRI ≠ 0: an interrupt is raised **instead** at the specified line;
  the 52-line counter interrupt is suppressed while PRI ≠ 0 (the counter itself
  keeps running — see note below).
- Comparison (evaluated every line):
  `{0,PRI7..PRI0} == {VC5..VC0, RC2..RC0}` — i.e. the ASIC compares
  `(char_line << 3) | raster_count` with the 8-bit PRI value; VC5 must be 0 for a
  match. [ARNOLD-REV] The register is consulted every HSYNC, so re-writing PRI
  after each interrupt yields multiple interrupts per frame. With a 312-line
  frame, line numbers ≥ 256 alias: PRI = n fires at line n **and** n+256.
  Line 256 itself is unprogrammable (PRI=0 disables). [QUASAR]
- **Trigger point**: on the **trailing edge of the HSYNC seen by the monitor**,
  with HSYNC width clamped at 6: for programmed widths ≥ 6 the interrupt
  position stops moving (fires at HSYNC_start + 6µs per [ARNOLD-REV]; [KT]
  measured "~10µs after HSYNC start" — ⚠ CONFLICT, treat [ARNOLD-REV]'s
  "trailing edge of monitor HSYNC, max 6" as primary). If the CRTC HSYNC is
  still active at the start of the next line, the interrupt can fire twice for
  one programmed line. [ARNOLD-REV §2.4]
- By contrast, the CPC-compatible 52-line interrupt (PRI=0) triggers on the
  trailing edge of the **CRTC** HSYNC (full programmed width matters).
  [ARNOLD-REV §2.4]
- PRI does **not** trigger during vertical adjust (R5) lines, and misbehaves for
  some values when R9 < 7. [ARNOLD-REV]
- When an ASIC raster interrupt occurs, bit 5 (top bit) of the Gate-Array 6-bit
  interrupt counter is cleared (as for a normal GA interrupt acknowledge), so a
  re-enabled CPC interrupt won't occur within 32 lines. [KT]
- Raster interrupt is cleared by CPU INT acknowledge, or by writing 1 to MRER
  bit 4 (as on CPC).
- Even in Gate-Array-compatible mode the Plus interrupt arrives ~1µs later than
  a real CPC. [QUASAR]

### IVR (`&6805`, W; bit 0 = 1 at reset, bits 7-1 undefined)

[ARNOLD-REV §2.7, WIKI-VIntBug, QUASAR, KT]

- The ASIC always supplies an interrupt vector byte on INT acknowledge (usable in
  IM 0 and IM 2; on a locked/plain Plus the bus byte is `&00` — some machines
  reportedly `&56` — vs typically `&FF` on CPC).
- Vector byte = `(IVR & &F8) | source | 0`:

| D2 D1 D0 | Source |
|---|---|
| 0 0 0 | DMA channel 2 |
| 0 1 0 | DMA channel 1 |
| 1 0 0 | DMA channel 0 |
| 1 1 0 | Raster (GA 52-line or PRI) |

- Priority: raster highest, then DMA2, DMA1, DMA0 lowest.
- **IVR bit 0** = DMA-interrupt auto-clear select: `0` ⇒ DMA interrupt flags in
  DCSR are cleared automatically by the INT acknowledge (and DCSR bits 4-6 are
  useless/frozen); `1` (reset default) ⇒ DMA interrupts must be acknowledged by
  writing 1 to the corresponding DCSR bit, and the request is held until acked.
- **Vectored interrupt bug** (hardware, all Plus/GX4000) [WIKI-VIntBug]: when the
  Z80 acknowledges an interrupt while executing an instruction located at an
  address with **A13 = 0** (i.e. in `&0000-&1FFF`, `&4000-&5FFF`, `&8000-&9FFF`,
  `&C000-&DFFF`), the ASIC sees a doubled/short IORQ and outputs the **DMA0
  vector (4)** instead of the raster vector (6) (and with auto-clear enabled the
  DMA vectors are affected too). Root cause: board logic (LK106/IC116) shortens
  or lengthens /IORQ based on A13. Workarounds: run code from A13=1 regions, or
  use IVR bit0=1 and re-dispatch by reading DCSR (which is always correct) at the
  head of the raster/DMA0 handlers. DMA1/DMA2 vectors are reliable. An FPGA
  implementation must decide whether to reproduce this (needed for some software
  that *relies* on DCSR re-dispatch? — harmless either way — but demos testing
  hardware may detect its absence).
- The ASIC does not decode RETI; expansion-bus daisy-chain (IEI/IEO) is not
  supported — expansion interrupts require IM 1. [ARNOLD-REV]

## 8. SPLT / SSA (screen split) and SSCR (soft scroll)

### SPLT `&6801` (W, POR=0), SSA `&6802`(hi)/`&6803`(lo) (W, POR=N)

[ARNOLD §2.3, ARNOLD-REV, QUASAR, KT]

- SPLT = scan line *after* which the split occurs; 0 = off. Comparison:
  `{SPLT7..0} == {VC4..VC0, RC2..RC0}` (8-bit; wraps, so with a 312-line frame a
  value fires at line n and n+256 — value `&37`/55 (or 56 per [KT] — ⚠ minor
  CONFLICT, likely off-by-one in one source) interacts pathologically with the
  frame end; avoid, or ensure SPLT=0 during vertical retrace, or set R5≠0).
- SSA is in CRTC R12/R13 format (same bit meanings, including the `&0C00`
  bank-size bits); it is the MA for the **first line after the split**, not a 16k
  block base. Any CRTC address is allowed (a split screen can itself scroll).
- Capture/apply timing [ARNOLD-REV §2.3 & "6845's MA"]: the CRTC (ASIC) keeps an
  internal "stored MA" reloaded into the MA counter at the start of each line.
  On the programmed line, the SSA value is captured when HCC == R1 (Horizontal
  Displayed) — or when HCC == R0 if VCC==R4 and RCC==R9 (last line of frame) —
  and is used from the next scan line onward, i.e. it *replaces* the line-start
  MA until the next split or frame restart (the split affects the rest of the
  screen).
- The value is never applied at VCC=0/RCC=0 (can't retarget the first line of a
  frame; it takes effect at the next opportunity, e.g. VCC=0/RCC=1).
- Multiple splits per frame are allowed (reprogram SPLT/SSA after each one).
- A split can occur during the **first** char-line of vertical adjust, but not
  later ones. [ARNOLD-REV]
- DRAM refresh is derived from the CRTC-generated address: keep split start
  addresses on 16k boundaries so address bits A1-A8 keep cycling, or RAM decays.
  Combining line-by-line vertical rupture (R4=0, R9=0) with raster interrupts
  can inhibit refresh entirely and corrupt RAM within seconds — real hardware
  hazard. [ARNOLD §2.3, QUASAR-plus]

### SSCR `&6804` (W, POR=0)

[ARNOLD §2.5, ARNOLD-REV, QUASAR]

| Bits | Function |
|---|---|
| D3-D0 | Horizontal delay 0-15 in **mode-2 pixels**: shifts image right; garbage pixels enter at left. Programmer must use multiples of pixels-per-byte-bit for the current mode (1/2/4 px steps in mode 2/1/0 — the shift is a bit-shift, so odd values in mode 0/1 scramble colours). |
| D6-D4 | Added to the low 3 bits of the scan-line (raster) address → shifts display **up** by 0-7 raster lines. |
| D7 | 1 = extend border over the **first 2 bytes (16 mode-2 pixels)** of each line to mask horizontal-scroll garbage. Keep set while H-scrolling. |

- Affects the whole main screen (both halves of a split); does **not** affect
  sprites.
- Effect is immediate (can toggle multiple times per line). The RA output =
  raster count + scroll value (≈ ANDed with &1F); the CRTC's internal counters
  are unaffected — hence odd behavior when R9 < 7, correct for R9 ≥ 7. For a
  clean full-screen vertical scroll the value must equal R9 when HCC==R1 (then
  the current MA is stored for the next line). [ARNOLD-REV]
- Vertical part pairs with R12/R13 coarse scroll for pixel-perfect scrolling;
  when V-scroll == 7 it takes precedence over the split-wrap bug case ([KT]).

## 9. DMA sound

[ARNOLD §2.6/2.7, ARNOLD-REV, QUASAR, KT, MAME]

Three independent channels fetch and execute 16-bit instructions ("AY-lists")
from **central RAM only** (64K address space `&0000-&FFFE`; top two bits select
DRAM page 0-3 of the base 64K; MMR/ROM mapping is ignored; bit 0 of the address
ignored — instructions are word-aligned, little-endian). Any channel may write
any PSG register. Max update rate = HSYNC rate (15.625 kHz standard) per channel;
DMA rate follows the CRTC line rate (vertical rupture at half-lines doubles it to
31.2 kHz [QUASAR]).

### Instruction set

| Encoding | Mnemonic | Action |
|---|---|---|
| `&0RDD` | LOAD R,DD | Write DD to PSG register R (R = 0-15) |
| `&1NNN` | PAUSE N | Wait N prescaled ticks (N=0-4095; PAUSE 0 = NOP) |
| `&2NNN` | REPEAT N | Load loop counter with N, mark next instruction as loop start (REPEAT 0 ≈ REPEAT 1; body executes N+1 times) |
| `&3xxx` | reserved | "Do not use". Observed on hardware to act as PAUSE NNN **then** REPEAT NNN [QUASAR/Zik — undocumented] |
| `&4000` | NOP | 64µs idle |
| `&4001` | LOOP | If loop counter ≠ 0: decrement, jump to instruction after REPEAT. If 0: no effect |
| `&4010` | INT | Raise this channel's interrupt (DCSR bit) |
| `&4020` | STOP | Stop channel: clears its DCSR enable bit; SAR left pointing at the **next** instruction |

- Control instructions decode: for opcode top nibble `4`, bits used are
  `?100 ???? ??ab ???c` (a=STOP,b=INT,c=LOOP; other bits ignored). Bit 15 is
  ignored for all instructions. Only **INT|STOP = `&4030`** is a valid/useful
  combination (`&4021` does not loop — LOOP bit ignored when STOP set). Non-`4xxx`
  combinations (`&6xxx` REPEAT+LOOP/STOP hybrids) have exotic undocumented
  behavior — don't rely on them. [QUASAR/Zik]
- Loops cannot be nested (one loop context per channel; a second REPEAT
  overwrites the loop start/counter). The ASIC never writes RAM (loop counters
  are internal). The REPEAT is not re-fetched on iterations (loop body is).
- **PAUSE**: total delay = `N × (PPR+1)` scan lines (64µs ticks); PPR (8-bit)
  counts N+1 lines per tick, giving 64µs..~67s. PPR changes take effect
  immediately, even mid-pause (a mid-pause PPR write advances the pause one
  iteration). A pause is not interruptible by SAR rewrites: pause keeps counting
  if SAR is rewritten; disabling the channel *suspends* pause countdown (state
  retained, resumes on re-enable). [ARNOLD-REV]
- SAR can be rewritten while the channel runs (list jump). Re-writing an already
  set enable bit is a no-op. On reset all channels stop.

### DCSR `&6C0F` (R/W; readable at any `&6C00-&6C0F`)

| Bit | R/W | Function |
|---|---|---|
| 7 | R | Raster interrupt occurred (set if last INT ack was raster) |
| 6 | R/W | DMA **channel 0** interrupt request (write 1 to clear) |
| 5 | R/W | DMA **channel 1** interrupt request (write 1 to clear) |
| 4 | R/W | DMA **channel 2** interrupt request (write 1 to clear) |
| 3 | — | unused (write 0) |
| 2 | R/W | Channel 2 enable |
| 1 | R/W | Channel 1 enable |
| 0 | R/W | Channel 0 enable |

Enable bits are set/cleared by CPU, cleared by STOP or reset; reading an enable
bit tells whether a list is still running. Interrupt bits: set on INT
instruction; cleared by CPU writing 1, or auto-cleared by INT-ack when IVR
bit0=0 (bugged — see §7). Raster interrupt has implicit priority: service DCSR
bit 7 first (it clears on ack; DMA bits persist).

### Timing & bus interaction

- Per HSYNC leading edge: 1 dead cycle (1µs), then one **fetch** cycle per
  active channel (enabled && not pausing), then **execute** cycles per active
  channel in channel order. All instructions execute in 1 cycle except LOAD =
  ≥ 8 cycles; +1 cycle if the CPU is simultaneously accessing the 8255, +2 if
  the CPU access is itself a PSG register write. [ARNOLD §2.6]
- The ASIC arbitrates the (integrated) 8255/PSG between DMA and CPU: CPU accesses
  to the 8255 can be **held off with wait states up to 8µs** during a DMA LOAD.
  After a LOAD the ASIC restores: 8255 port A direction, selected AY register,
  and AY read/write state. No other Z80 cycle stealing is documented (DMA RAM
  fetches occur during HSYNC using the video/refresh slots). ⚠ MISSING — no
  authoritative statement on whether DMA RAM fetches ever stall the Z80; assume
  no (fetches sit in the GA's existing memory slots) unless hardware testing
  shows otherwise.
- Hardware hazard (do not need to emulate, but don't generate): reducing HSYNC
  width with DMA lists running can cause internal contention "in the worst case
  causing irreversible damage to the ASIC". [WIKI-ASIC]

## 10. Analog inputs (ADC0-7, `&6808-&680F`, read-only)

- 8 channels, 6-bit (0 = 0V … `&3F` = 2.5V), updated ~200×/s; only 4 channels
  wired to the DB15 connector (two analog paddles/joysticks: ch0 = X1, ch1 = Y1,
  ch2/ch3 = second device axes per [KT] tests). Writes ignored.
- Defaults with nothing attached (464+ measurement): `3F 3F 3F 3F 3F 00 3F 00`
  (ADC5 and ADC7 read 0 — used by firmware to sense machine config; wiring
  differs on GX4000). [ARNOLD §2.9, ARNOLD-REV, KT]
- Analog joystick fire buttons map onto digital joystick 0's fire 0/1 (keyboard
  matrix). No ghosting between digital joysticks/analog fire/keyboard on Plus
  (keyboard-internal clash remains). [ARNOLD-REV §2.18]

## 11. Cartridge & boot

### Physical / mapping

[ARNOLD §2.8, ARNOLD-REV, QUASAR]

- Cartridge = up to 512 KB (4 Mbit) = **32 pages × 16 KB**, addressed by 5
  ASIC-driven upper address lines (CA14-CA18). No onboard ROM in the machine at
  all — firmware lives in cartridge page 0.
- **High bank (`&C000-&FFFF`)** selected via classic ROM-select port `&DFxx`:
  - value 128-255 (`&80-&FF`): low 5 bits select cartridge **physical page 0-31**
    directly (logical ROMs 128-159).
  - value 0-127, ≠ disc ROM code: physical page 1 ("BASIC").
  - value 0 or 7 (disc ROM code): physical page **3** ("AMSDOS") — on
    464+/6128+; **on GX4000 selecting 7 still yields page 1** (disc hardware
    select absent). [ARNOLD-REV]
  - Expansion ROMs via ROMDIS still override matching page numbers.
- **Low bank** (position set by RMR2 D4-D3, page by RMR2 D2-D0): physical pages
  0-7 only.
- **Reset state**: RMR2 = 0 ⇒ cartridge page 0 at `&0000-&3FFF`, ASIC page off,
  `&DFxx` = 0 ⇒ page 1 at `&C000` on GX4000; on 464+/6128+ the /EXP line decides:
  /EXP low ⇒ page 1, else page 3 (CP/M auto-boot). Boot simply starts the Z80 at
  `&0000` executing cartridge page 0 (which contains the firmware on system
  carts, or the game's own boot code on game carts). [ARNOLD-REV §2.8]
- Standard system cartridge layout (128 KB): 0 = firmware, 1 = BASIC, 2 = blank/
  game, 3 = AMSDOS, 4-6 = Burnin' Rubber, 7 = BASIC copy. [ARNOLD §3, QUASAR]

### CPR file format

[WIKI-CPR — originally cpctech]

- RIFF container. Every chunk: 4-byte ASCII id + 4-byte little-endian length.
- File starts with the `RIFF` chunk; its data begins with the 4-byte form-type
  **`Ams!`**, followed by the block chunks. RIFF length = file size − 8.
- Block chunks are named **`cb00` … `cb31`** (ASCII decimal — `cb00` = cartridge
  block 0 → `&0000-&3FFF`, `cb01` = block 1, etc.), each carrying up to 16 KB.
  A short chunk is zero-padded to 16 KB by the loader; oversized data beyond
  16 KB is ignored.

### ACID (protection chip)

[WIKI-ACID, KT]

- 16-pin chip inside licensed cartridges (Amstrad 40908) generating a serial
  keystream (SIN) from a 17-bit LFSR (taps 0,9,12,16), clocked at 4 MHz (CLK),
  reset via /CCLR (preload `&1FFFF`), perturbed by EPROM address lines A0-A7 and
  /CE via per-cycle XOR patterns (nocash's reverse engineering, full algorithm on
  the wiki page: `CmpVal=&13596, XorVal=&C820` + per-address-line XOR constants;
  if `/CE=0 && (ShiftReg|&100)==CmpVal` then `ShiftReg ^= XorVal`; shift right,
  feedback to bit 16; SIN = bit 0).
- If the ASIC doesn't see the expected stream it "does scatter access to RAM,
  making the cartridge unusable". Exact ASIC-side check timing is unknown even
  to the reverse engineers.
- **Emulators do not emulate ACID at all** — they simply omit the ASIC-side
  check ([MAME] has no ACID code; CPR loads and runs). A MiSTer core should do
  the same: load CPR blocks into cartridge ROM space and never fail. (Real
  hardware can also run ACID-less via a timing exploit — irrelevant to
  emulation.)

## 12. Model differences: 464+ / 6128+ / GX4000

[ARNOLD §1, WIKI-GX4000, QUASAR-plus]

| Feature | 464 Plus | 6128 Plus | GX4000 |
|---|---|---|---|
| RAM | 64 KB | 128 KB | 64 KB |
| Keyboard | full (CPC6128 matrix) | full | none — Pause button = 'P' key; 2 digital joypads on matrix lines 9/6 (joystick mapping as CPC); keyboard lines 0,1,2,4,5,7,8 unconnected |
| Tape | yes | no | no |
| FDC (µPD765 + SED9420) | no (PCB space present) | yes | no |
| Analog paddle port | yes (4 ch wired) | yes | yes (paddles shipped) |
| Printer port | yes | yes | absent (inputs float) |
| Expansion port | yes | yes | absent (/ROMEN, ROMDIS, /RAMRD, RAMDIS, CURSOR, /EXP, BUSY unconnected) |
| Master clock | 40.000 MHz | 40.000 MHz | **39.90257 MHz** (= 9 × 4.43619 MHz for PAL composite lock) → whole machine 0.25% slower |
| Video out | RGB (monitor) | RGB | RF/composite (+RGB) |
| `&DFxx`=7 (disc ROM) | page 3 | page 3 | **page 1** (no disc select hw) |
| Boot | cart page 0 at &0000; /EXP selects page 1 or 3 at &C000 | same | cart page 0 at &0000, page 1 at &C000 |

Common Plus-vs-CPC deltas relevant to a core: PPI is an imperfect ASIC emulation
(port B always input, port C always output; control-register rewrite does *not*
clear output latches — breaks some CPC keyboard scanners; port A input mode
presents `&FF` to the PSG bus) [KT, ARNOLD-REV §2.15]; printer BUSY sampled only
~500×/s [QUASAR-plus]; colour changes ~½µs later than CPC and old-CPC colours
approximated through the RGB table [KT, WIKI-ASIC]; joystick ports lack the
third fire line; 4 MHz bus is actually 4.44 MHz-derived timing for some signals.

## 13. CRTC "type 3" (the ASIC's CRTC) — summary of differences

(Brief — a separate CRTC-focused document covers depth.) Sources: [WIKI-CRTC],
[KT crtcnew + cpcplus].

- Port decode (`&BCxx-&BFxx`, b1b0 of address): `00` select (W), `01` write data
  (W), `10` **read data** (R), `11` read data (R) — i.e. both read ports return
  the selected register; there is **no separate status register port** (unlike
  type 1's `&BExx` status).
- On the Plus, `IN` on `&BCxx`/`&BDxx` *also performs the corresponding write*
  with the open-bus byte (see §4) — a major compatibility trap.
- Register **reads repeat modulo 8**, mapping to:

| Selected reg (mod 8 pattern over 0-31) | Returns |
|---|---|
| 0, 8, 16, 24 | R16 (light pen H) |
| 1, 9, 17, 25 | R17 (light pen L) |
| 2, 10, 18, 26 | "Status 1" (internal state; bits flag HCC==R0/2, HCC==R1, HCC==R2, last HSYNC char, last VSYNC line — active-low) |
| 3, 11, 19, 27 | "Status 2" (bit7=0 when RC≠0, bit5=0 when RC==R9, rest unknown) |
| 4, 12, 20, 28 | **R12** (readable — unlike types 1/2) |
| 5, 13, 21, 29 | **R13** |
| 6, 14, 22, 30 | (unmapped — open bus) |
| 7, 15, 23, 31 | (unmapped — open bus) |

- R3: both HSYNC width (0⇒16) and VSYNC width (0⇒16) programmable, like type 0.
- No R31 dummy register. CRTC type 4 ≡ type 3 (register reads repeat the same
  way).
- Type-3 detection by software: unlock ASIC, page ASIC RAM, check it exists.

## 14. Known hardware flaws checklist (decide emulate / ignore)

1. **IM2 vector corruption when interrupted code has A13=0** (§7). Deliberate
   choice needed; software workarounds mean most titles run either way.
2. **RAM refresh loss** with R4=0/R9=0 rupture + raster interrupts (RAM decays in
   ~10s on hardware) [QUASAR-plus]. A core with SDRAM doesn't naturally decay —
   arguably skip.
3. **External RAM expansion write-through of ASIC page writes** (§2).
4. **PPI emulation quirks** (§12) — these are *required* for compatibility, they
   are the Plus behavior.
5. **Open-bus reads** returning the last instruction byte for write-only I/O and
   unmapped ASIC addresses (§4) — needed by some detection code.
6. **IN on GA/CRTC ports performs writes** (§4/§13) — needed ("Into the Eagles
   Nest").
7. ASIC-damage HSYNC/DMA contention — do **not** emulate destruction; ignore.
