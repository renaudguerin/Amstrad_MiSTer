# ASIC graphic-mode latch — 4 November 2026

## Position

The ASIC decoder now consumes a separate qualified mode-update event. It rejects
one-microsecond HSYNC pulses, accepts exact-two-microsecond pulses and requests made
during a valid pulse, and keeps the ASIC's long-pulse request window open through
raw-HSYNC+7us rather than classic+6us. The existing monitor/sync/IRQ event and CRTC
write acceptance remain unchanged.

A retained actual-GA-to-video regression fails before the repair and passes after it,
including requests actually stored between +6/+7us and after +7us. An in-flight
snapshot control rejects a phantom event and verifies the pending request on a fresh
pulse. The initial private experiment below explains why simply connecting the old
classic-reference MODE_SYNC_EN was insufficient. Cross-provider Opus review accepted the production change; its requested test and
comment follow-ups passed the final44-bench selection. SHAKER comparison on a new
RBF remains pending; no hardware acceptance is claimed here.

The reported DSC4 credit-name corruption is motivation for this investigation,
not evidence of its cause. Neither this test nor emulator agreement identifies the
mode request/pulse sequence used by those exact title pixels.

## French source and limits

The existing pdf-inspector inspection report and primary Markdown for French ACCC
v1.11 were reused from the main checkout's `docs/classic/extract/inspector-v1.11-fr/`.
The report is `native_partial`; its fallback pages do not include this material.
`lookup.py` was used for navigation only (Jev unavailable). French pp.52–57 were
rendered with `pdftoppm` and visually read. Renders are in the ignored
`local/overnight-20261103/asic/mode-latch/fr-052.png` through `fr-057.png`.

- **§9.3.1 p.52:** every CPC, explicitly CRTC0 through4, needs an HSYNC of at least
  two microseconds for a mode change. The GA's requested-mode register changes in
  the third microsecond of OUT(C),r8. ASICs defer HSYNC by one microsecond, as they do
  character display. The qualification rule therefore includes Plus/type3; it is
  not a classic-only inference.
- **§9.3.3 p.53:** the type3/4-specific chart permits requests made during HSYNC to
  affect that pulse's result, until the delayed GA qualification window closes.
  An implementation which samples only at raw HSYNC assertion cannot satisfy this.
  A long pulse's GA interval is capped at six microseconds (§9.3.1), so "trailing"
  here means the qualified GA interval's end, not necessarily raw HSYNC's final edge.
- **§9.3.4.1 p.54:** changing mode within a line requires R3>1. Its exact first
  redisplayed/mixed pixel is documented for0/1/2/4 and explicitly left open for3.
  The type4 chart on p.57 must not be used as an exact type3 dot oracle. The private
  vector therefore scores constant-data decoded pens several characters after the
  pulse; it makes no assertion about the first transition pixel or mixed byte.

These pages establish the minimum-width and during-pulse request contracts. They
do not by themselves prove an exact master-clock dot for the ASIC mode latch.

## Pre-fix production boundary

At baseline8dde1e7, `asic_video.v` sampled GAMODE on raw HSYNC rising, inside PIXEN. Its adjacent comment
explicitly defers the minimum-width rule. `asic_ga_timing.v` stores the RMR shadow
and exports it unsynchronized on both MODE and GAMODE_O. Its hdelay sequencer also
exports MODE_SYNC_EN; the motherboard leaves that event unconnected. The classic
GA video path instead receives the sync-generator mode event. Those are current
code facts, not the source oracle.

The smallest interface change worth investigating is an explicit qualified mode-
update enable into `asic_video`, wired to the GA event at each integrated caller.
The decoder would consume that one-clock event in the CLOCK domain, with reset and
SNA_LOAD priority preserved; it must not mask it with PIXEN. This changes the mode
latch, not the raw HSYNC/counter/blank/IRQ pipeline. However, the existing event's
exact-two-microsecond integration failure below blocks adopting that wiring alone.

A scratch-only copy of `asic_video` adds MODE_SYNC_EN and consumes GAMODE on that

| Request during valid four-us pulse | PASS |
| Request after qualification closes | PASS |

Final output: `mode-latch: FAIL`, exit1. Overlay sources and full logs are
`asic_video.event-overlay.v`, `mode_latch_top.event-overlay.sv`,
`build-event-overlay.log`, and `event-overlay.log` in the same directory.

Source inspection explains the observed gap: raw HSYNC begins after a CLKEN edge.
The hdelay sequencer first advances0→1 one character later, then1→6 on the same edge
that an exact-width2 pulse falls. Its combinational reset clears bit2 before the
stored hdelay2d can preserve a high level, suppressing MODE_SYNC_EN. A width4 pulse
has time to establish that state. This is a specific integration observation; it
is not permission to shift hdelay, HSYNC, or CRTC clock phase. A bounded fix must
make the two-us mode-qualification contract work while retaining those existing
signals and IRQ contracts, or explicitly return with evidence that this cannot be
done within that boundary.

## Retained delayed-window repair and final proof

Rendered French §9.3.3 p.53 is an additional acceptance boundary: for a long raw
HSYNC beginning at R2, the classic GA interval closes at R2+6, whereas the ASIC's
one-microsecond-delayed interval closes at R2+7. The retained test therefore stores
RMR=82 through the real GA at raw-start+405 master clocks (6.328125us), and separately
at+469 clocks (7.328125us). Driver guards assert the **observed GA storage** is
strictly inside the intended six-to-seven or seven-to-eight-us window. Both pulses
are14us long; decoded pens are scored three characters after their final raw edge,
so these cases do not assert type3's unresolved first mixed pixel.

The additional source-derived fail-first command was:

```sh
make -C sim/plus asic-mode-latch
```

With the retained fixture added and production still on the parent's restored raw-I/O
baseline, `retained-before.log` records three failures: short1us, during-valid4us,
and before-ASIC-deadline. Each has32 wrong decoded dots, with RMR request2 actually
stored. The exact-two, after-seven, after-eight and absent-pulse controls pass.
Final line: `asic-mode-latch: FAIL`, make exit2. The preceding private deadline proof
is preserved separately in `before-with-deadlines.log`.

Implementation is limited to a new `ASIC_MODE_SYNC_EN` event/state in
`asic_ga_timing.v`, an explicit `MODE_UPDATE_EN` input in `asic_video.v`, and their
motherboard/test-caller wiring. A fresh raw pulse opens the mode-only tracker; a
pulse ending before two character intervals is discarded. A valid pulse qualifies
one character after its raw fall, capped at raw-start+7us for long pulses. This is
separate from the existing hdelay/MODE_SYNC_EN, monitor sync, blanking, IRQ, PRI,
sprite and CCLK contracts. No opcode or alias-specific logic was added. The decoder
consumes the one-CLOCK event without PIXEN gating. Reset and settled SNA mode load
retain priority; snapshot apply discards the mode tracker's unrecorded pulse history
and does not manufacture a new rising pulse from restored HSYNC.

The permanent owner is `sim/plus/asic_mode_latch_test{.cpp,_top.sv}`, registered as
fast `run/asic_mode_latch_tests` in the normal Plus suite and TESTS index, with
`asic-mode-latch` as its focused alias. It instantiates the actual GA/video modules;
only external VRAM is constant FFFF. Expected visible pens15/1 come from independent
mode0/mode2 bit decoding. Existing leaf t05f now pins the explicit decoder-event
input; real pulse qualification belongs to this integration regression. The p1 and
p8 fixtures connect the actual event rather than substitute a timing equation.

After the final code edit, the same focused command passes all seven pulse/deadline

### Named residual: ASIC mode/blank alignment

For R3low=2..6 with active display after the pulse, current blanking ends at raw
HSYNC fall, while the new mode event arrives one character later. An entire old-mode
character can therefore remain visible between them. This is a **16-dot model
alignment residual**, materially coarser than the unresolved type3 mixed-pixel
transition in French §9.3.4.1 p.54. It must not be described merely as that open
first-pixel question. The ASIC's delayed blanking needs a separate bounded repair
and source/hardware checks; raw HSYNC, blanking, clocks and IRQ remain unchanged in
this mode-only unit. Normal border-only sync hides this mode-dependent display gap.
