# SHAKER D1-27 stall at `wait_ssm 0x0305` (2026-10-27)

**Current position, 2026-10-28:** the `0305` stop is overcome on release
`321f96a` by a scratch copy of the script with sufficient, slower keyboard
input. The unmodified script still fails. This is evidence for a script/input
problem, not an established CRTC wedge. See the bounded control below.

**Original observation (2026-10-27): reproduced on the device, cause then unknown.** On delivered `cec641c`,
`CSL_27/MODULE D/SHAKER-D-1.CSL` (CRTC 1, `shaker26.dsk` `f7082f8e…`, Full,
`--tolerate-capture-timeout`) again produced 30 captures and then
`no SSM #0305 arrived within 120s`. That is the same result as October attempts a4–a7, so the stall is deterministic.

The method is the one used for [the CRTC0 wedge](crtc0-ssm-wedge-2026-10-27.md): save an SNA from
the stalled machine through the OSD and pull it with `sna_pull.py`. Evidence (ignored):
`docs/references/shaker-ssm-wedge-2026-10-27/D1-27-*` in the main checkout.

The single snapshot (`D1-27-stall.sna`) shows:

- CPU in a fixed delay loop at `A2F3`: `DEC DE; LD A,D; OR E; NOP; JP NZ,A2F3`, then
  `JP (HL)` with HL=`A2FD`, DE=`00E9`, interrupts off, SP=`405D`;
- CRTC 1: R3=6, R4=38, R5=0, R6=26, R7=30, R9=7; C4=26, C9=2; no VSYNC or HSYNC flag.

Interpretation: that loop always terminates, so one sample cannot distinguish a wedge from
a slow wait. Unlike the CRTC0 case, the CRTC state here looks like a normally counting frame
(C4 < R4, R7=30 reachable). Repeat saves did not register: after the first save Main's OSD cursor
stays on the item, and F12 + Enter did not save again (generation stayed 1). So the
second sample, the one that would show progress, is missing.

## Next step

1. Take two or more SNAs from the stalled state. Reload the core between saves to reset the OSD
   cursor (this loses the state, so it cannot work), or find the OSD key sequence that re-arms
   `Save snapshot` from its retained cursor. Check it on a running core first.
2. If PC keeps cycling through `A2F3`/`A2FD` and C4 advances, the program is alive and waiting
   on something. Disassemble the caller at `A2FD` from the SNA RAM to find the condition.
   The October D1-27 captures `02E3`–`0304` show the page sequence up to the stall.

## 2026-10-27 follow-up: not explained by the CRTC 0 wedge fix

The [CRTC 0 IVM-exit fix](crtc0-ivm-exit-wedge-fix-2026-10-27.md) changes only the type-0
engine. D1-27 runs on CRTC 1, and its snapshot shows a normally counting frame, so that fix
cannot account for this stall. The next step above still stands: take several SNAs, then
disassemble the caller at `A2FD`.

## Release-build follow-up, 2026-10-28

The [unattended evidence unit](../session-logs/classic-overnight-2026-10-28.md)
reproduces the same `0305` stop on released `321f96a`. Stack disassembly
corrects the proposed next step: A2FD is delay-return padding; the caller at
710B repeats an interactive sweep. The supplied script sends fewer spaces
than the sweep needs, and the saved state has accepted fewer again. A slower,
sufficient-input control is needed before attributing this stop to CRTC state.
Additional input after snapshotting was inconclusive, and repeat-save
navigation still did not produce a new generation. No RTL change follows.

## Sufficient-input device control, 2026-10-28

The unmodified supplied script stops at `wait_ssm 0305` on released `321f96a`
after 30 captures, with no capture failures. A scratch copy preserves the
same boot, media and preceding tests, then changes the final interactive sweep:

- before the 36-space burst following `0302`, set
  `key_delay 250000 250000 400000`;
- extend its later 11-space burst to 13 spaces (49 total);
- stop immediately after observing `0305`.

On the same RBF this completes: `status=success commands=69 captures=31
capture_failures=0 ssm_records=41`. The native `0305` capture shows the module
menu, confirming return from the sweep. No snapshot was saved during this
control. The original source script and RTL are unchanged.

The disassembly starts the loop at length `40`, count `3A`, and decrements
until count `09`: 49 accepted advances. The source script supplies 47 spaces
after `0302`; prior snapshots retain length `16`, count `10`, corresponding
to 42 advances. The control changes count and pacing together; it does not
establish a minimum reliable count or isolate key repeat/debounce behavior.
Markers emitted inside the key burst were drained afterwards: `0303`, `0304`
and `0305` captures show the same menu. This proves progress through the stop,
not capture alignment or numeric correctness of every swept page, and not a
pass for the rest of module D.

Evidence is retained, untracked, under
`docs/references/classic-overnight-2026-10-28/d1-slow49-a1/` in the task checkout:
manifest, scratch CSL and final PNG. The `0305` PNG SHA-256 is
`a19dd2468c297808bea6cab6a0e0ab6a41943f04c1b84a2cc6fd5738eb23c230`.
The manifest verifies original CFG restoration. Snapshot re-arming remains a
separate unresolved tooling question; it is no longer a prerequisite to
classifying this bounded D1 stop.
