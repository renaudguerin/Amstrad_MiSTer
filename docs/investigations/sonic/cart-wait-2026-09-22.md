# Sonic rearm: cartridge wait latency against the READY-only rule

Investigation from `56771ff`, 22 September 2026. No MiSTer device or AmSpirit
instance was used. Evidence comes from the existing
[rearm-boundary trace](rearm-boundary-2026-09-22.md), primary-source scrapes,
the production-T80 D5 fixture and new scratch traces.

## Answer

**Yes: the 85-tick STOP-selection miss is explained by a modelled cartridge
latency that disagrees with the reference.** The model loses one whole
microsecond on every cartridge read whose MREQ starts two master ticks into a
microsecond. Between the FBF9 fetch and F922 the rearm path makes eight such
reads (six of them NOP/opcode fetches), so it takes 49 µs where the READY-only
rule gives 41 µs. Nine such reads precede the SAR low store; removing their
576 ticks turns the 85-tick miss into a margin of about 491 ticks in that
trace. The scratch Sonic counterfactual below reports what the whole title
schedule does once the penalty is removed.

The rule is settled by sources, so the fail-first vector and a minimal RTL fix
are in this branch. Device acceptance is still required.

## Reference rule

- The Gate Array/ASIC READY output drives Z80 /WAIT and is the only CPU
  arbitration. It "also applies to ROM access and to RAM expansions. So the
  Z80 always runs at the same speed, regardless of the type of memory being
  accessed", with every instruction stretched to whole microseconds
  (`local/scrapes/Gate Array - CPCWiki.pdf`, "Every microsecond").
- The 160-pin CPC+ ASIC drives the cartridge `/ROM` and `CA14`-`CA18` itself
  and has a single `READY` output; the pin-out has no other CPU wait source
  (`local/scrapes/Gate Array and ASIC Pin-Outs - CPCWiki.pdf`, 160-pin ASIC).
- Therefore cartridge code runs at the RAM rate: NOP 1 µs, `LD HL,nn` 3 µs,
  `DEC HL`/`INC HL` 2 µs, `POP HL` 3 µs, `LD HL,(nn)` 5 µs, `JP (HL)` 1 µs.
  These are the Zilog T-state counts rounded up to 4 T-states per µs.

### Reference timing of the rearm path

AmSpirit's correctly based mapped CPU memory
(`docs/screenshots/sonic-phase-2026-09-22/mapped-cpu-8000.bin`, ignored)
gives the cartridge bytes. The executed path matches the trace's fetch
addresses exactly:

| Address | Instruction | µs |
| --- | --- | ---: |
| FBF9 | `POP HL` | 3 |
| FBFA-FC05 | 6 × (`DEC HL`; `INC HL`) | 24 |
| FC06 | `LD HL,(8325)` | 5 |
| FC09, FC0A | `NOP`; `NOP` | 2 |
| FC0B | `JP (HL)` to F91C | 1 |
| F91C-F91E | 3 × `NOP` | 3 |
| F91F | `LD HL,835A` | 3 |
| **FBF9 to F922** | | **41** |

The earlier AmSpirit witness put FBF9 at beam X 144 and F922 at X 800, a
difference of 656. If its X unit is one 16 MHz pixel (1,024 per 64 µs line),
that is exactly 41 µs. The unit is still uncalibrated, so this is agreement,
not the authority; the instruction count above does not depend on it.

## Model mechanism

The fixture uses the production `rtl/sdram.v`, `plus_cartridge_memory`,
`plus_mmu`, `asic_ga_timing` and T80pa netlist with production clocking. The
cartridge read path is therefore deterministic: from MREQ the stall lasts 17
master ticks (request, wait for the next 8-tick SDRAM arbitration slot, six
clocks to data, two register stages back to `cart_stall`).

In the rearm trace every microsecond has the same structure (phases are
master ticks within the microsecond):

- READY is high at phases 6 to 26.
- T80pa samples WAIT on the CEN_n edge of T2 and holds the T-state when it is
  low. It latches an opcode on the following CEN_p, and other read data one
  CEN_n later.
- A read whose MREQ starts at phase 2 has its only in-window WAIT sample at
  phase 18. The cartridge stall is still high there (it falls at phase 20),
  and at the next sample (phase 34) READY is low, so the cycle waits for the
  next microsecond: **+64 ticks**.
- Reads starting at phases 34 or 50 already miss READY at their first sample;
  the stall has ended before their in-window sample, so they cost nothing.

Stall pulses in the trace, grouped by starting phase:

| Stall start phase | Whole trace | FBF9 to F922 | FBF9 to SAR low |
| ---: | ---: | ---: | ---: |
| 3 (MREQ at 2) | 32 | **8** | **9** |
| 35 | 13 | 12 | 12 |
| 51 | 36 | 5 | 7 |

An example is the FC06 operand read: MREQ at 653631490, stall
653631491-653631508, WAIT sampled low at 653631506, READY gone by 653631514,
T3 only at 653631578, 64 ticks later than without the stall.

A steady cartridge NOP chain always lands on phase 2: in RAM each NOP takes
64 ticks at that phase, so the penalty makes every cartridge NOP 2 µs.

The data itself is early enough. It reaches `cart_dout` 18 ticks after MREQ,
while T80 latches an opcode at 24 ticks and read data at 32. The stall held
WAIT until the byte arrived, which is two ticks too pessimistic.

## Fail-first vector

`make -C sim/plus d5-cart-timing` (also in `make -C sim production-t80-test`,
so CI's production-t80 job runs it). It boots a synthetic CPR on the D5
production-T80 fixture: `DI`, 64 `NOP`, 16 `LD HL,nn` with distinct operands,
`LD (4000),HL`, `HALT`. It requires the exact opcode fetch sequence, the last
operand stored in RAM, and steady-state fetch intervals of 64 ticks per NOP
and 192 per `LD HL,nn`. Expectations are derived on paper from the READY
window and T80pa WAIT sampling; the first NOP and the NOP-to-LD transition are
excluded because their fetch starts are at different phases (the transition
gap is 176 ticks, also worked out on paper in the test).

Before the fix: NOP gaps 128, `LD HL,nn` gaps 256, test fails. After: 64 and
192, operands latched, test passes. Reverting only the RTL makes it fail again.

Collateral contract changes, both re-derived rather than read back:
`p0_boot_tests` now checks the byte at the earliest T80 latch instead of at
stall release (data measured 7 clocks after release: 6 fails, 7 passes), and
`p10_boot_tests` pins the stall run at 11 − 7 = 4 ticks.

## Fix

`sdram.v` emits `cart_grant`, a one-clock pulse on the arbitration edge that
admits the cartridge request. `sna_cart_mux` passes it to its default owner.
`plus_cartridge_memory` turns it into `cpu_granted`, qualified by the current
CPU request and cleared on completion, cancellation, discard or any control
operation. `plus_mmu` drops `cart_stall` when granted instead of when data
returns. Timing budget:

- grant at edge I; `cart_ack`/data at I+6; `cart_dout` at I+9;
- `cart_stall` low after I+2, so the first WAIT sample that can see it high is
  I+3;
- T80pa latches an opcode 8 ticks after that sample and read data 16 after,
  so no earlier than I+11, two ticks after the byte is on `cart_dout`.

A read not yet admitted (refresh due, another client owning the slot, the
SNA save borrowing the port) keeps the stall and stays safe. That contention
remains an FPGA artifact; it is rare because idle slots reset the refresh
debt and the CPU uses at most one of eight slots per microsecond.

## Sonic counterfactual

Three scratch production-T80 D5 builds on the unchanged original CPR
(SHA-256 `4cb31c7f…ed887ae`), cap 1,280,000,000 ticks, stopping 8,000,001
ticks after the first acknowledge, using the
[phase discriminator](phase-discriminator-2026-09-22.md)'s `prepare.py`,
`trace.cpp` and `analyze.py`. All use current `asic_dma.v` (with B20-1).

- **nofix**: this branch with `cart_granted` tied to 0 in the fixture top,
  which is exactly the old data-return stall.
- **fix**: this branch.
- **fix + PAUSE**: this branch plus the `a137d48` terminal-PAUSE rule ported
  onto current `asic_dma.v` in the scratch copy only. That candidate's own
  file no longer builds against the B20-1 port list.

| Observation | nofix | fix | fix + PAUSE |
| --- | --- | --- | --- |
| A021 raw CRTC line, successive lists | 231, 255, 279, 303 | 9, 32, 55, 78 | 7, 7, 7, 7 |
| List recurrence (312-line frame) | 336 (+24) | 335 (+23) | **312 (+0)** |
| `PAUSE 7; INT` handler spacing | 9 lines | 9 lines | **8 lines** |
| DMA2 disable/re-enable per list | every list | never | never |
| Split captures in window | 23, drifting | 0 | every list, lines 7, 15, 23 … 247 |
| Acknowledges | 163 | 163 | 173 |

Reading:

- The fix removes exactly one line per list. DMA2's enable never clears
  because the CPU's SAR reload now lands before STOP is selected, so STOP is
  never executed. This is the rearm-boundary miss disappearing, not a DMA
  rule change.
- The remaining +23 lines are the separate PAUSE terminal-edge line (nine
  instead of eight lines per `PAUSE 7`).
- The two together give a frame-locked 312-line list with 8-line handler
  spacing. That matches the fresh AmSpirit normal-boot control (A021 on the
  same line every frame, 8-line intervals). The split registers are now
  captured at the same comparison lines every frame.
- `a137d48` measured 313 lines alone, which is 312 plus the one restart line
  this fix removes. Its failed hardware acceptance was obtained with the
  cartridge penalty still present, so it does not by itself reject the PAUSE
  rule. Whether PAUSE plus this fix passes on hardware is a new, separate
  question.

These are model counterfactuals, not hardware evidence. Run times were 854 s,
712 s and 436 s.

## Limits and next step

- This is model and source evidence. Device acceptance on Sonic is still
  required and belongs to the device owner; nothing here claims the title
  renders correctly.
- The rule covers cartridge ROM reads only. RAM and I/O paths are unchanged.
- TV80-based fixtures use a different WAIT/data sampling model; their green
  gate is regression coverage, not timing evidence.
- Device acceptance order (owner's call): this branch alone first, since
  it is source-settled; then this branch plus the terminal-PAUSE rule. The
  PAUSE rule stays a separate DMA change with its own vector and review; it
  is not in this branch.
- The `no_wait` speed hack can drop GA writes regardless of this change (an
  OUT can miss both GA latch windows). The P10 video-coherence test now runs
  with the production READY wait; the defect is a separate task.
