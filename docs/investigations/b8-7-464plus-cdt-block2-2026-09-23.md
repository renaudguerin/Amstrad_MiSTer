# B8-7: 464+ CDT playback lost block 2 (resolved, 2026-09-23)

Defect: on a 464+ with `Plus_EN.cpr`, `RUN"` on `AmstradDiag.cdt` printed `Loading
DIAG.BIN block 1`, then `Found DIAG.BIN block 3` / `Rewind tape` through block 7. Block 2
never loaded. Report and device procedure:
[device record](hardware-runs/device-acceptance-cdcb3c3-2026-09-22.md), section "B8-7:
real CDT playback on 464+ loses block 2".

## Result

Fixed on master by the cartridge execution-rate fix `63fcf23` ("Release the Plus
cartridge stall at SDRAM admission") and its follow-up `94b18f0`. The failing device run
used RBF `4027f5e`, which predates both. Before the fix every cartridge-ROM opcode fetch
lost a microsecond (cartridge NOP 2 us instead of 1 us, pinned by `d5-cart-timing`). The
464+ firmware lower ROM is cartridge page 0, so its tape routines ran on wrong timing; the
classic 6128 control ran its firmware from SDRAM ROM and was unaffected.

Device bisection, 2026-09-23, one run per RBF, identical stimulus (464+ CFG
`600024f7…4e47`, `Plus_EN.cpr` `3ce35dfc…81ae`, `AmstradDiag.cdt` `203775c2…2ee7`,
keypad 1 then `tape-uk.json` then `space.json`, native captures from 15 s to 130 s after
Space):

| RBF | Has `63fcf23` | Has B20-7 DMA fix `64702ac` | Result |
| --- | --- | --- | --- |
| `4027f5e` | no | no | Block 2 lost (same screens as the original report) |
| `ef8da61` | yes | no | `Loading DIAG.BIN block 2` at 25 s; Amstrad Diagnostics v1.3a by 100 s |
| `64702ac` | yes | yes | Same; 25 s and 100 s frames byte-identical to `ef8da61` |

`ef8da61` differs from `4027f5e` in RTL only by `63fcf23` + `94b18f0`, minus `4027f5e`'s
two-line CPR OSD ungate (which `64702ac` carries while still loading). `64702ac` differs
from current master only by the tape-bank move `859fd24`, which does not touch Plus
models. The firmware-level mechanism (why block 2 specifically was lost) was not traced;
no further work is needed for it.

Evidence (main checkout, gitignored): `docs/screenshots/b8-7-464plus-cdt-2026-09-23/`
(captures `zz_b87_*` = `64702ac`, `zz_b87b_*` = `ef8da61`, `zz_b87c_*` = `4027f5e`, MGLs,
device scripts). The CFG was restored to `2e585b4c…d8e4` after each run.

## Simulation fixture (not kept)

A `cdt-boot` fixture was built from the stalled attempt's P10-based adapter (production
T80 netlist, cloned Amstrad.sv tape path, tzxplayer GHDL netlist). It was discarded
without committing, because the regression it would guard is already pinned by
`d5-cart-timing`.

What it established, for anyone reviving it:

- Boot to BASIC Ready takes 87 M ticks; the fixture runs at about 1.26 M ticks/s.
- Ctrl + keypad Enter (default expansion `RUN"` + Return) reaches `Press PLAY then any
  key:`, and Space is accepted. Keyboard input works; no firmware RAM injection is needed.
- Output capture must hook the lower-ROM target of the `0xBB5A` jumpblock
  (`CF FE 93` -> `0x13FE`), not `0xBB5A` itself: the cassette manager calls TXT OUTPUT
  directly, so a `0xBB5A` hook sees BASIC's output but never the tape messages. The prior
  attempt's "no PLAY prompt" was this capture blind spot.
- Open divergence: the firmware writes BSR `0x09` to port F7 (`pc=0x2BCF`, CAS START
  MOTOR at `0x2BC1`), then runs its 2 s spin-up delay and the edge-sampling loop at
  `0x2B4x`, but the fixture's `mb.portC[4]` never rises and tzxplayer never plays. Hardware
  on the same RTL starts the motor, so this is a fixture defect; its cause was not found.
